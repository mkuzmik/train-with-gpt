# Idea: a living athlete profile (proposal, for review)

Not implemented. This proposes an athlete profile: a short, always-current
document about who the athlete is right now, loaded at the start of every
consultation and kept up to date from data, interviews and results.

## Problem

The server keeps two kinds of memory today:

- **Goals** (`goals.md` or `goals/<user_id>.md`): where the athlete is
  heading. One document, rewritten as a whole with `save_goals`.
- **Notes** (`notes/...`): an append-only daily log.

Neither holds the durable facts a coach needs every time: race results and
PBs, current fitness, baselines (resting HR, HRV range, usual sleep, weight
trend), test results, injury history, weekly availability and limits, what
has and hasn't worked, gear. These end up scattered across daily notes, so
the coach has to rediscover them each consultation and often doesn't (see
`consultation-context.md`). Goals are not the right place either: they change
on a different cadence and mixing the two makes both harder to keep current.

## Proposed solution

### What the profile holds

A single Markdown file per athlete, kept short (target: under ~1–2 pages) since
it is loaded every time. Details stay in notes. Every entry carries an
`as of` date and a source: `data`, `interview` or `note:<date>`.

| Section | Examples | Source |
|---|---|---|
| Background | years training, sports, history | interview |
| Race results and PBs | table: date, event, distance, time, conditions | data (races, best efforts) + interview |
| Current fitness | 4- and 12-week volume per sport, longest run/ride, best efforts, fitness/fatigue/form, thresholds and zones | **computed** |
| Baselines | resting HR, HRV band, usual sleep, weight trend | **computed** |
| Tests and labs | lab tests (VO2max, thresholds), blood work the athlete chooses to record | interview, notes |
| Health | injury history, current niggles, recent illness | interview, notes |
| Constraints | available days and hours, equipment, weekly limits, life load | interview |
| What works | responses to blocks, tapers, fueling, heat | learned from notes, confirmed by athlete |
| Preferences | training style, how they like to be coached | interview |
| Gear | shoes/bikes and their mileage | **computed** |
| Current block | phase, focus, key sessions this week | coach + athlete |

The "current block" section could also be its own file if it churns too much;
see open questions.

### Two kinds of entries

- **Computed** sections are regenerated by the server from Strava and
  intervals.icu, with no model involved. They never go stale and are never
  hand-edited.
- **Stated** sections (everything the athlete told the coach) change only
  through the interview or with the athlete's explicit confirmation. The
  computed side never overwrites them.

### Tools

1. **`read_athlete_profile`**: returns the profile. `start_consultation`
   includes it automatically (see `consultation-context.md`).
2. **`refresh_athlete_profile`**: recomputes the computed sections from data.
   It also returns *suggestions* for stated sections, e.g. "an activity marked
   as a race on <date> isn't in race results; add it?". Suggestions are never
   applied automatically.
3. **`update_athlete_profile(section, change, source)`**: updates one
   section. Section-level updates keep concurrent sessions from overwriting
   each other's changes, and each update is its own git commit, so history is
   the audit log.
4. **`profile_interview`**: guidance like `discuss_goals`, but it first gets
   the list of missing and stale sections from the server and asks only about
   those, one question at a time.
5. **Save hook**: `save_consultation_notes` returns a short checklist ("new
   result? injury change? availability change?") so the coach proposes profile
   updates at the end of a conversation.
6. **Staleness**: the profile's read output marks sections past a threshold
   (e.g. constraints unconfirmed for 90 days) and conflicts with data (e.g.
   a faster best effort than the recorded PB), and the coach mentions them.

### Storage and format

- `profile/<user_id>.md` in the training repo (`profile.md` on the personal
  stdio path), next to goals. This follows the existing user-scoping in
  `helpers.py` and keeps all personal data out of this public code repo.
- Fixed `##` section headings with a small metadata line per section
  (`<!-- source: interview; as_of: 2026-01-31 -->`), so the server can update
  one section without parsing free text. Humans can still read and edit it.
- Writes go through the same git sync as notes and goals, including the
  concurrent-write handling from the notes-sync fix.

### Backfilling from history

Existing athletes have months of notes. A one-off "build from history" flow:
the coach reads all notes plus a data refresh, drafts each stated section with
`note:<date>` sources, and the athlete confirms section by section before
anything is saved.

## Alternatives considered

- **Put it all in goals.** One file, no new tools, but goals get rewritten
  wholesale, and mixing slow facts with changing targets makes both worse.
- **Structured JSON/YAML instead of Markdown.** Easier to validate, harder for
  athletes to read and edit on GitHub. Markdown with fixed headings is a
  middle ground.
- **Let the model rewrite the whole profile after every consultation.** Simple,
  but it drifts, loses details and races with concurrent sessions.

## Open questions

- Is "current block" part of the profile, or a separate `plan` file?
- Which sections should be computed on every `start_consultation`, and which
  only on explicit refresh (Strava rate limits are per application)?
- Stale thresholds per section.
- Should blood work and lab data live here at all, or only in notes?

## Rollout

1. File format, `read_athlete_profile`, `update_athlete_profile`, and
   inclusion in `start_consultation`.
2. `refresh_athlete_profile` for the computed sections; depends on data tools
   from `more-training-data.md` (weekly totals, best efforts, baselines).
3. `profile_interview`, the save hook and staleness markers.
4. Backfill flow for existing athletes.

## How to verify

- Unit tests: section-level update leaves other sections byte-identical;
  computed refresh never touches stated sections; metadata round-trips.
- Concurrency test: two `update_athlete_profile` calls on different sections
  at once both land.
- Integration test: profile is per user and shows up in `start_consultation`.
- Manual: after backfill, a fresh conversation states race results and
  targets without reading any notes.
